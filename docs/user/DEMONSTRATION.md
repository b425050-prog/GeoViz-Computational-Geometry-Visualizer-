# Demonstration guide

**Status:** Planned demonstration runbook; retain and update for the completed application. Demonstrate only implemented/verified features. Do not use concept GIFs as evidence that code is running.

## 1. Prepare before presenting

Use a known source revision, configuration and dataset generation. Start server/console through verified instructions. Prepare member, creator and authorized analyst accounts without exposing passwords. Confirm general/restricted benign media, normal reference history, a campaign scenario and a genuine-complaint scenario.

Keep evidence records, an offline proposal/report and a labelled concept fallback available. If live networking/graphics fails, state the failure and use actual prior recordings where available; do not describe artwork as recorded execution.

## 2. Main demonstration: approximately 15 minutes

These are presentation durations, not measured performance targets.

| Segment | Suggested duration | What to show and explain |
| :--- | :--- | :--- |
| Problem and scope | 1 minute | Explain unusual volume versus coordinated behaviour versus report validity. |
| Website | 2 minutes | Registration/login, a photo, native video and server-enforced restricted access. |
| Event trail | 1 minute | Submit a report manually, retry safely and inspect the durable event/count. |
| Normal and campaign activity | 3 minutes | Baseline, bounded seeded cohort, surge and behaviour plane. |
| Investigation | 3 minutes | Linked history/map/targets, missing evidence and content-policy review. |
| Legitimate alternative | 2 minutes | Viral/genuine complaint scenario; explain why a surge is not guilt. |
| Case and evidence | 2 minutes | Record a decision, inspect audit and export the run settings. |
| Limits and results | 1 minute | Actual measured results, failures and next steps. |

## 3. Algorithm demonstration: approximately 10 minutes

Use one hand-computable preset per mode. Show hull orientation/popping; membership edge/vertex boundary; Dijkstra relaxation; A* g/h/f and equal optimal cost; DBSCAN neighbourhood/core/border/noise. Pause and rewind one trace, then change input to demonstrate invalidation.

Explain why operation counts are independent of playback speed. Do not promise that A* expands fewer vertices on every graph or that an index accelerates every dense DBSCAN scene.

## 4. Final submission pack

Include source/build manifests, actual setup/run guide, proposal, full report, OOP map, test/evaluation artifacts, sample scenes/media licenses and real screenshots/GIFs. Institutional signatures or certification must come from the institution; this documentation does not provide them.
